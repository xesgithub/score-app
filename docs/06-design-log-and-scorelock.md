# Design — Activity Log (Admin) + ระบบล็อกการให้คะแนน

> ✅ **สถานะ: implement แล้ว** — Log (v0.4.0), ล็อกคะแนนทั้งชุด (v0.4.0), ล็อกคะแนนรายทีม (v0.5.0)
> ครอบคลุม 2 ฟีเจอร์: (A) Log, (B) ระบบล็อกการให้คะแนนเพื่อกันกดผิด
>
> **สรุปสิ่งที่เลือกทำจริง:**
> - Log: Admin เห็นทั้งหมด · กรรมการเห็นเฉพาะของตัวเอง · เก็บ `score.set` เฉพาะค่าที่เปลี่ยนจริง
> - แจ้งกรรมการว่ามีการบันทึก (ℹ️ notice) เพื่อความโปร่งใส/PDPA
> - Lock: **รายทีม** (กรรมการล็อกทีมตัวเอง กันกดผิด, ปุ่มหลังชื่อทีม) + **ทั้งชุด** ("ยืนยันคะแนนของฉัน" ขั้นสุดท้าย) · กรรมการปลดล็อกเองได้
> - ประวัติ/Log รีเฟรชอัตโนมัติหลังมีการเปลี่ยนแปลง

## ส่วน A — Activity Log (ให้ Admin ดูได้)

### A.1 เป้าหมาย
ให้ Admin เห็นว่า "ใคร ทำอะไร เมื่อไหร่" — เพื่อตรวจสอบย้อนหลัง (audit) เช่น กรรมการคนไหนแก้คะแนน, Admin ล็อก/ปลดล็อกตอนไหน, ลบอะไรไป

### A.2 ขอบเขต event ที่ควรเก็บ
| หมวด | event | actor | ตัวอย่างรายละเอียด |
|------|-------|-------|----------------------|
| คะแนน | `score.set` | judge | team X · หัวข้อ Y · 3 → 4 |
| การแข่งขัน | `competition.status` | admin | open → closed |
| การแข่งขัน | `competition.update` | admin | แก้ชื่อ |
| หัวข้อ/ทีม/กรรมการ | `criterion.create/update/delete` ฯลฯ | admin | เพิ่ม "การนำเสนอ" |
| กรรมการ | `judge.token_revoke` | admin | สร้าง token ใหม่ |
| ล็อกคะแนน (ส่วน B) | `score.lock` / `score.unlock` | judge/admin | กรรมการ 1 ยืนยันคะแนน |

> เริ่มต้น (MVP) แนะนำเก็บเฉพาะ event สำคัญ: `score.set`, `competition.status`, `score.lock/unlock`, การ delete ต่าง ๆ — ส่วน create/update ทั่วไปเพิ่มทีหลังได้

### A.3 Data Model — ตาราง `ActivityLog` (ใหม่)

```prisma
model ActivityLog {
  id            String   @id @default(cuid())
  competitionId String                       // log ผูกกับการแข่งขัน (ดู/ลบตาม cascade)
  actorType     String                       // "admin" | "judge" | "system"
  actorLabel    String                       // เช่น "Admin" หรือ "กรรมการ 1" (เก็บ ณ เวลานั้น)
  action        String                       // เช่น "score.set", "competition.status"
  detail        String?                      // ข้อความอ่านง่าย (ไทย) พร้อมแสดงในตาราง
  metadata      String?                      // JSON string (ค่าก่อน/หลัง, id ที่เกี่ยว) — optional
  createdAt     DateTime @default(now())

  competition   Competition @relation(fields: [competitionId], references: [id], onDelete: Cascade)

  @@index([competitionId, createdAt])
}
```

เพิ่ม relation ใน `Competition`: `activityLogs ActivityLog[]`

หมายเหตุการออกแบบ:
- **เก็บ `actorLabel` เป็น snapshot** (ไม่ใช่ FK ไป judge) เพราะกรรมการอาจถูกลบภายหลัง แต่ log ต้องคงอยู่
- `detail` เก็บข้อความไทยสำเร็จรูป → frontend แสดงได้เลยไม่ต้อง map
- `metadata` เป็น JSON string (SQLite ไม่มี native JSON) — ใช้เก็บ before/after เผื่ออยากดูละเอียด

### A.4 จุดบันทึก log (write path)
ทำเป็น helper กลาง `logActivity(competitionId, actor, action, detail, metadata?)` เรียกจากจุดที่เกิด event:
- `judge.ts` → หลัง upsert score สำเร็จ (`score.set`)
- `admin.ts` → หลังเปลี่ยน status, delete, revoke ฯลฯ

> ⚠️ ข้อควรระวัง: `score.set` เป็น auto-save ทุกครั้งที่กดปุ่ม → log จะโตเร็ว
> **ทางเลือกลดจำนวน:** เก็บเฉพาะเมื่อค่าเปลี่ยนจริง (ค่าใหม่ ≠ ค่าเก่า) และ/หรือ debounce (log ครั้งสุดท้ายต่อช่องภายใน N วินาที) — แนะนำเก็บเมื่อค่าเปลี่ยนจริงพอ

### A.5 การมองเห็น log (Visibility) — Admin เห็นทั้งหมด + กรรมการเห็นเฉพาะของตัวเอง ⭐

ยึดหลัก privacy เดิมของระบบ (ฝั่ง judge filter ด้วย `judgeId` เสมอ เห็นแค่ของตัวเอง) — log ใช้หลักเดียวกัน:

| ผู้ใช้ | เห็นอะไร |
|--------|----------|
| **Admin** | log ทั้งหมดของการแข่งขัน (ทุกกรรมการ + ทุก action) |
| **กรรมการ** | เฉพาะ log ที่ตัวเองเป็น actor (การให้คะแนนของตัวเอง) — **ไม่เห็นของกรรมการคนอื่น** |

> เหตุผลไม่ให้กรรมการเห็นของคนอื่น: กันอิทธิพลต่อการตัดสิน (เห็นว่าคนอื่นให้เท่าไร) — สอดคล้อง NFR-1 (privacy) เดิม

### A.5.1 API (อ่าน)
```
# Admin — เห็นทั้งหมด
GET /api/admin/competitions/:id/logs?limit=100&offset=0&action=score.set
    → { logs: [{ id, actorType, actorLabel, action, detail, createdAt }], total }

# กรรมการ — เห็นเฉพาะของตัวเอง (filter ด้วย judge จาก token ฝั่ง server)
GET /api/judge/logs?token=...&limit=50&offset=0
    → { logs: [{ id, action, detail, createdAt }], total }
```
- เรียงใหม่→เก่า, paginate; ฝั่ง judge บังคับ filter actor = judge ของ token นั้นเสมอ (ป้องกันดูข้ามคน)

### A.6 UI
**Admin** — แท็บ/ปุ่ม "📜 ประวัติ (Log)" ในหน้ารายละเอียดการแข่งขัน
- ตาราง: เวลา · ผู้ทำ · การกระทำ · รายละเอียด + ตัวกรองประเภท event · โหลดแบบ paginate

**กรรมการ** — ส่วน "ประวัติการให้คะแนนของฉัน" (พับเก็บได้) ใต้ตารางให้คะแนน
- แสดงเฉพาะของตัวเอง: เวลา · ทีม/หัวข้อ · ค่าเก่า → ค่าใหม่
- ช่วยให้กรรมการทวนว่าตัวเองกดอะไรไป (เสริม pain point "กันกดผิด" — เห็นย้อนหลังได้)

### A.7 ผลกระทบ / ข้อควรพิจารณา
- **DB โต:** SQLite บน Azure Files โหลดต่ำ รับได้ แต่ควรมีปุ่ม/นโยบายลบ log เก่า หรือเก็บเฉพาะ event สำคัญ
- **Performance:** เพิ่ม insert 1 แถวต่อ action — กระทบน้อย; มี index `(competitionId, createdAt)` ช่วย query
- **Migration:** เพิ่มตารางใหม่ → `prisma migrate` (ไม่กระทบข้อมูลเดิม)

### A.8 ความโปร่งใส — แจ้งกรรมการว่ามีการบันทึก (แนะนำ: แจ้ง) ✅
การเก็บ log `score.set` = บันทึกว่า "กรรมการคนไหนทำอะไรเมื่อไหร่" ซึ่งผูกกับตัวบุคคล → เข้าข่ายข้อมูลส่วนบุคคล (PDPA)

**ข้อเสนอ: แจ้งให้กรรมการทราบ** เพราะ
1. **ความโปร่งใส/ไว้ใจ** — รู้ว่าระบบตรวจสอบได้ ยุติธรรม ไม่ใช่จับผิดลับ ๆ
2. **PDPA** — หลักการคือควรแจ้งเจ้าของข้อมูลว่ามีการบันทึกและเพื่อวัตถุประสงค์ใด (ตรวจสอบความถูกต้องของการให้คะแนน)
3. **ต้นทุนต่ำ** — ข้อความบรรทัดเดียวในหน้ากรรมการ ไม่กระทบ flow

**ข้อแลกเปลี่ยน:** ถ้าไม่แจ้ง กรรมการอาจให้คะแนนเป็นธรรมชาติกว่า แต่เสี่ยง PDPA + ความรู้สึกไม่ดีถ้ามารู้ทีหลัง → โดยรวม "แจ้ง" คุ้มกว่า

**รูปแบบที่เสนอ** — ข้อความเบา ๆ ใต้ตาราง/ตอนเปิดลิงก์ครั้งแรก:
> ℹ️ ระบบบันทึกการให้คะแนนเพื่อการตรวจสอบความถูกต้อง (เวลาและการแก้ไข)

> หมายเหตุ: นี่เป็นมุมมองเชิงปฏิบัติด้านความโปร่งใส ไม่ใช่คำแนะนำทางกฎหมาย
> หากเป็นงานทางการ/เดิมพันสูง ควรให้ฝ่ายกฎหมายตรวจถ้อยคำแจ้งเตือนอีกครั้ง

## ส่วน B — ระบบล็อกการให้คะแนน (กันการกดผิด)

ตีความได้ 2 ระดับ — เสนอทั้งคู่ให้เลือก (แนะนำ **B1** สำหรับ pain point "กดผิด")

### B1 — กรรมการล็อกคะแนนของตัวเอง (Submit / Confirm)  ⭐ แนะนำ
**แนวคิด:** กรรมการกรอกครบแล้วกด **"ยืนยันคะแนนของฉัน"** → คะแนนถูกล็อก แก้ไม่ได้ กันการเผลอแตะปุ่มผิดภายหลัง หากต้องแก้จริงต้องกด **"ขอแก้ไข"** (unlock) ก่อน

**Data model:** เพิ่มใน `Judge`
```prisma
scoresLockedAt DateTime?   // null = ยังแก้ได้, มีค่า = ล็อกแล้ว
```
(ล็อกทั้งชุดของกรรมการคนนั้น — ตรงกับ use case "กรอกเสร็จแล้วปิด")

**พฤติกรรม:**
- กรรมการ lock → ปุ่มคะแนนทั้งหน้าเป็น read-only + ป้าย "✅ ยืนยันแล้ว"
- backend: `PUT /judge/scores` ปฏิเสธ (409) ถ้า `scoresLockedAt != null`
- unlock ได้ 2 นโยบาย (เลือก): (a) กรรมการ unlock เองได้, หรือ (b) เฉพาะ Admin ปลดให้ — **แนะนำ (a)** เพื่อความคล่องตัว งานเล็ก
- Admin เห็นสถานะ "ยืนยันแล้ว/ยังไม่ยืนยัน" ต่อกรรมการ (ต่อยอด progress ได้)

**API เพิ่ม:**
```
POST /api/judge/scores/lock?token=...      // ยืนยัน (ล็อก)
POST /api/judge/scores/unlock?token=...    // ขอแก้ไข (ปลดล็อก)
```

### B2 — กันกดผิดระดับปุ่ม (confirm ก่อน save)
**แนวคิด:** ไม่เพิ่มสถานะล็อก แต่เปลี่ยน UX ให้กดผิดยากขึ้น — เหมาะเสริมกับ B1
ตัวเลือย UX (เลือกได้หลายอย่างรวมกัน):
- **แยกจังหวะ select vs save:** แตะเลือกคะแนน (ไฮไลต์) แต่ยัง **ไม่ save ทันที** → ต้องกด "บันทึกแถวนี้" (ลดพลาดจากปัดโดนบนมือถือ)
- **Undo toast:** หลัง save ขึ้น toast "บันทึก 4 แล้ว · เลิกทำ" ~5 วิ (กลับค่าเดิมได้)
- **ยืนยันเมื่อทับค่าเดิม:** ถ้าช่องมีคะแนนอยู่แล้วและกดค่าใหม่ → ถามยืนยัน

> ปัจจุบันเป็น auto-save ทันที (`setScoreValue` → `save`) ซึ่งเสี่ยงกดผิดบนมือถือ
> **แนะนำ:** B1 (ล็อกทั้งชุดเมื่อจบ) + Undo toast จาก B2 — คุ้มค่า/แรงน้อย ครอบคลุม pain point

### B3 — (ทางเลือกเสริม) Admin ล็อกรายทีม
ล็อกคะแนนเฉพาะทีมที่แข่งจบแล้ว (ทุกกรรมการแก้ทีมนั้นไม่ได้) — ตรงกับที่จดไว้ใน CHANGELOG 0.1.0
ซับซ้อนกว่า (ต้องมีตาราง lock ต่อ competitor) — เสนอไว้เป็น phase ถัดไป ไม่รวมรอบนี้

### B.4 ความสัมพันธ์กับ "closed" ที่มีอยู่แล้ว
- `competition.status = closed` = ล็อก **ทั้งการแข่งขัน** (มีแล้ว)
- B1 = ล็อก **รายกรรมการ** (ละเอียดกว่า, กรรมการคุมเอง)
- ทั้งคู่ทำงานร่วมกันได้: save จะถูกปฏิเสธถ้า *อย่างใดอย่างหนึ่ง* ล็อก

## สรุปสิ่งที่ต้องตัดสินใจก่อนลงมือ
1. **Log:** เก็บทุก event หรือเฉพาะสำคัญ? (แนะนำ: สำคัญก่อน) · เก็บ `score.set` ทุกครั้งหรือเฉพาะค่าที่เปลี่ยน? (แนะนำ: เฉพาะที่เปลี่ยน)
2. **Lock ระดับไหน:** B1 (กรรมการล็อกเอง) ✅ / B2 (confirm กันกดผิด) / ทั้งคู่ / รวม B3 ภายหลัง
3. **ใครปลดล็อก B1:** กรรมการเอง (แนะนำ) หรือเฉพาะ Admin
4. ขอบเขตรอบนี้: ทำทั้ง A+B หรือแยกเป็น 2 รอบ (เช่น B ก่อน เพราะกันพลาดระหว่างงานจริง)
